# payment-service: ручное подтверждение оплаты

Платёж создаётся автоматически после резервирования заказа. Для локальной проверки
доступны просмотр платежей и ручное подтверждение по `paymentId`. Настоящие списания
не выполняются. Авторизация пока не подключена; позже эти операции будут доступны
только администраторам.

## Запуск

Из корня проекта:

```powershell
docker compose up -d --build --wait order-service inventory-service payment-service
```

Также можно запустить приложения из IDE с существующими PostgreSQL и Kafka.

## Проверка с заказом

1. Создайте товар с остатком через Swagger inventory-service.
2. Создайте заказ через `POST /api/orders` в order-service.
3. Дождитесь статуса `WAITING_FOR_PAYMENT`: склад резервируется через существующую Kafka-цепочку.
4. В [Swagger payment-service](http://localhost:8083/swagger-ui/index.html) выполните
   `GET /api/payments`. В списке найдите платёж по `orderId` и возьмите его `paymentId`.
5. Выполните `POST /api/payments/{id}/confirm`, передав `paymentId`. Тело запроса не нужно.
6. Ответ содержит текущее состояние платежа. Список платежей также отражает результат.

Создавать платёж вручную и отправлять события в Kafka не требуется.
После подтверждения payment-service публикует `PaymentSucceeded` в `payment.events`.
Обработка результатов в order-service пока не подключена, поэтому статус заказа
после оплаты сам не изменится.

## API

- `GET /api/payments` — все платежи, сначала новые.
- `POST /api/payments/{id}/confirm` — подтвердить платёж по его ID и вернуть состояние.

Повторное подтверждение возвращает сохранённый результат без нового события.
Подтверждение неизвестного платежа возвращает 404.
Если срок оплаты истёк, платёж переходит в `FAILED`, публикуется `PaymentFailed`
с кодом `SESSION_EXPIRED`. Успешный или неуспешный результат окончателен для попытки.

## Обработка события заказа

Сервис слушает `order.events` с группой `payment-order-events-v1` и обрабатывает
`OrderReadyForPaymentEvent`. Остальные типы событий пропускаются без записи в inbox.

- Для платежа генерируется собственный UUID. Он не совпадает с идентификатором события.
- Первая попытка имеет номер 1. Повторный `eventId` пропускается через inbox.
- Повторная готовность заказа с другим `eventId` и теми же пользователем, суммой
  и валютой возвращает существующий платёж с прежним `paymentId`.
- Срок оплаты рассчитывается от `occurredAt` по `app.payment.expiration-minutes`
  и по умолчанию составляет 15 минут.
- Если событие доставлено после срока оплаты, сразу сохраняются `FAILED`
  и `PaymentFailed` с кодом `SESSION_EXPIRED`.
- При создании обычного платежа сохраняются inbox и `PENDING`. При подтверждении
  изменение статуса и событие outbox сохраняются в одной транзакции.
- При сбое БД изменения откатываются. Kafka error handler повторяет временные ошибки.
- Невалидные сообщения, неподдерживаемые версии и конфликты данных попадают в
  `order.events.payment-service.dlt`. Временные ошибки после исчерпания повторов — туда же.
- Publisher отправляет результаты из outbox в `payment.events` с ключом `orderId`.

Платёж, inbox и outbox сохраняются в БД и переживают перезапуск.
При недоступной Kafka события остаются в outbox для повторной отправки.
Сообщения выбранного пакета отправляются асинхронно, как в inventory-service.
Каждый результат обрабатывается отдельно после ответа Kafka; poller ждёт завершения
всего пакета перед следующим циклом. Строгий порядок событий заказа этим не гарантируется.
Обновления outbox выполняются отдельным executor: 2 потока, очередь размером с пакет.
Таймаут доставки Kafka — 30 секунд, таймаут запроса — 10 секунд, ожидание метаданных
и буфера — до 5 секунд на вызов. Возврат зависших `PROCESSING` настроен на 60 секунд.
Автоматическое завершение просроченных платежей, повторные попытки оплаты,
возвраты и обработка результата в order-service будут следующими этапами.
